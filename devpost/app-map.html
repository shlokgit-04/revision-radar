Revision Radar app map

One page, no backend. The scheduler is a pure function; everything else is state + render.

The re-plan path (the kernel, traced)

1. app.js — #slipBtn.onclick
Pushes today into state.lostDays, then triggers the re-plan click.
2. app.js — #replanBtn.onclick
Calls RR.buildPlan(chapters, examDate, today, lostDays) and stores the result with state.lastDiff = RR.diffPlans(old, new).
3. plan.js — buildPlan()
Walks dates backwards from the exam, skips lost days, reserves the eve, runs the tier loop (revision passes drop first), and returns {days, cuts, panic}.
4. app.js — renderPlan()
Renders the rail and turns the diff into the "Plan re-cut: 2 pass(es) dropped · 5 block(s) moved" banner.

Everything else, in one breath

State + storage: app.js > save/load, one localStorage key, written on every mutation.
Setup screen: app.js > renderSetup() — add-row, inline weight/confidence edits, live panic meter.
Today screen: app.js > renderToday() — checkboxes keyed by date+chapter+kind, written straight to ticks.
Tests: test/plan.test.js — ordering, eve rule, compression tiers, diff counts, degenerate dates.
Practice to reuse: before changing a shared engine, write the assertion that would catch the change. Group 4 of the tests ("re-plan moves blocks and the diff sees it") is what caught the diff bug before it ever shipped.
